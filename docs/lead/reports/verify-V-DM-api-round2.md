### MEDIUM

**N1. A chat that already exists still lets a blocked person tell "blocked" from "messages off" or "suspended"; and `GET /dm/with` shows a banned person as 404.**
`api/src/dm/dm.service.ts:372` (`mineOrGone` hides a chat for a block either way), `:575-595` (`withPerson`: `conversationId: null` when blocked, `404` for BANNED), `conversations()` (hides blocked people).
Run (vh1, five modes, each with one earlier message from S to R): *R blocks S* or *S blocks R*: both people's inbox has 0 rows, `GET …/messages` 404, unread 0, `with` = `200 {acceptsMessages:false, conversationId:null}`. *R turns messages off* or *R suspended*: the chat stays in both inboxes, `messages` 200 and readable, `with` = `200 {acceptsMessages:false, conversationId:<the chat>}`, inbox row `acceptsMessages:false`. *R banned*: `with` = **404**, but inbox and messages still 200.
So the refusal is neutral (H1 closed) but a person who had a chat with someone and is then blocked sees the chat vanish, while "messages off" leaves it in place: they can tell. A person with no earlier chat cannot tell blocked from off (both `with` bodies are identical), but can tell *banned* (404) from everything else.
Should: an owner ruling. Either accept that a block hides the whole chat (the app already answers `BLOCKED_BY_USER` on reply and react, and hides blocked people everywhere), and say so in the brief; or keep the chat visible read-only for the blocked person with `acceptsMessages:false`, and make `with` answer a banned person like a suspended one. I did not rank it HIGH because the new-contact case, the one a stranger can probe, is neutral.

**N2. The gate does not heal a stale `verifiedUntil`, so a person who has just renewed after a lapse is refused with "Subscribe and get verified to send messages." for up to ten minutes.**

Run (vh1): an APPROVED person whose `verifiedUntil` was yesterday, with a new ACTIVE subscription ending in 60 days: `POST /dm/messages` → `403 verification_required`. After `VerificationService.fresh()` on the same person → `201`. (A queued second plan that extends a running first one is fine: after the job `verifiedUntil` moves from +1 h to the end of the queued plan, 11 Feb 2027, and `canSendDm` stays true.)
Should: in `send` (or inside `canSendDm`), call `fresh()` first when the columns say "approved but past", exactly as the ideas route does. This is the same function the owner defined as "the one place".
