**N-5. SKIP: what the server does (ruling needed, item 10).** `surveys-public.service.ts:285-325` (`event`), `:226-237` (`openable`), `:168` (placement).
- Did: one person sends SKIP once, twice, three and four times for one survey; another person sends VIEW, START, SKIP, SKIP then submits; one person SKIP once then submits; one person submits then SKIPs; one person whose first SKIP is 20 days old.
- What the server does: **every SKIP request stores one event row** (no per-day or per-survey de-duplication) until the person has 2 (`surveys.max_skips`, default 2, no config row set). **After the 2nd, the survey is hidden from that person for good**: `GET /surveys/{id}` 404, events 404, placement does not offer it, and **the answer route 404 "We could not find that survey."**. The 3rd and later SKIPs are 404 and are not stored. Days do not matter (a 20-day-old SKIP counts; no reset). START and VIEW do not protect against it. After a person has answered, SKIP is 204 and stores nothing.
- So **yes, a web page that sends SKIP on each reload locks a person out**: VIEW, START, SKIP (reload), SKIP (reload), then submit → 404, nothing stored, the person sees "not found". One SKIP followed by an answer works (201). Stored SKIP rows for the 4-SKIP person: 2 (not 4). In the released report `skips` counts the rows, so skips from one person are at most 2.
- Should: the lead decides; the web must send SKIP only when the person really dismisses the card, never on load, and not once a START has been sent for the same survey (the server does not check that).
