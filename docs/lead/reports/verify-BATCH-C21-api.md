# New findings

## HIGH 1 (C2, so also C2.1). The start time is set once and never again: a new release that boots and is then put back, or any later `deploy.sh rollback api`, leaves the old code (which never links a charge to its post) serving after the stamp; the next boot of the new code refunds those posts and they stay
- Code: `api/src/talk/charge-sweeper.service.ts:56-72` (`stampStart`, only when the start time is null, "later boots never move it"; called from `onModuleInit`, i.e. at every boot of the new code, before the health check). `infra/deploy/deploy.sh:201-209` (`roll_api`: restart the new release; if `/api/health` does not answer, `undo_switch api` and restart the old release) and `:271-282` (`rollback api`: go back to the previous release). On origin/main `attachRef` has no caller, so every charge the old code makes has `refType/refId` null.
- What I did (database migrated from origin/main's own `prisma/`, then the new migration; real jest-booted processes of each tree): boot the new code (start time stamped). Then the old code (origin/main tree, a real process) takes 4 posts through the API: a paid post that stays, a paid post whose answer I then deleted, a free-post person, and a paid post aged 90 days. Boot the new code again (start time unchanged, as designed). Sweep at +31 minutes.
- What happened: `paid-kept` charge `REVERSED`, 1 REVERSAL ledger row, **the answer still stored** (the person has the post and the money back); `free-kept`: charge `REVERSED`, **the free post given back, the answer still stored**; `paid-nopost`: reversed (correct). The charge I aged to 90 days (so it is dated before the stamp) stays `COMMITTED`, as it should. The second sweep (+2 hours) changes nothing.
- Why it is reachable tonight: a failed health check after a successful boot (the port, the database or Redis check fails after `onModuleInit`) puts the old release back, and `deploy.sh rollback api` is a documented command; both leave the old code serving for as long as it is wanted, and the first deploy of this batch is the only one whose previous release is the old code. After the next successful deploy every post the old code took in between is refunded 30 minutes after that boot. Nothing in `infra/RUNBOOK.md` or the deploy script says to clear the start time. This is the same class as the first check's HIGH 1, moved from "migrate" to "boot".
- Should: either (a) `deploy.sh`: in `undo_switch api`/`rollback api`, after the old release is back, `UPDATE "ChargeSweeperState" SET "startAt" = NULL` (the next boot of the new code stamps again, later than anything the old code took); or (b) a rule for tonight: no `rollback api` and no health-failed fallback without running that statement first. Not a code change in the API. The lead may rule (b) and call this closed for tonight; as the code and scripts stand it is open.
