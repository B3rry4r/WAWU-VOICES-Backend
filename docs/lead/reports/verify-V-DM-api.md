## Findings

### HIGH

**H1. A refusal tells a blocked person they are blocked, apart from "messages are off".** `api/src/dm/dm.service.ts:47` (`blocked`), `:203` (`dm_closed`), `:49` (`recipient_unavailable`), `:199-201`.
Run (B1): same sender, four receivers. Receiver blocked the sender: `403 blocked`. Sender blocked the receiver: `403 blocked`. Receiver has "Let people message me" off: `403 dm_closed`, message "This person is not taking messages." Receiver suspended/banned/deletion pending: `403 recipient_unavailable`. Receiver deleted or no such id: `404 NOT_FOUND`.
Result: the three codes are all distinguishable, so a person who was blocked learns "blocked" and not "messages off". The owner's brief says a refusal should not let them tell. It also leaks a suspended/banned state (`recipient_unavailable` vs `404`).
Should: one code and one message for blocked-either-way, messages-off, and receiver-unavailable (the `NEUTRAL` text already exists), and the same HTTP status as the not-found case or all of them the same. `GET /dm/with/{id}` already does this right (`acceptsMessages:false` for both, run B1 "with when closed"/"after block"). Note the existing app already answers `BLOCKED_BY_USER` on reply/react (`me/blocks.ts:87`); the owner should say if DMs follow that or the neutral rule. The brief for this task says neutral.

### MEDIUM

**M1. A moderator removal of a DM sends the sender an "Appeal" notice that cannot be used.** `api/src/admin/trust/moderation.service.ts:981-990` creates a `MODERATION_NOTICE` ("A post of yours was taken down", `targetType: "dm_message"`, appealable groupKey). `api/src/talk/talk.controller.ts:112-114` (`AppealDto`) still accepts only the five old target types.
Run (MOD1): reported DM removed by a moderator; sender got the notice; `POST /appeals` with `DM_MESSAGE` → `422 VALIDATION_FAILED`; with the notice's own targetType uppercased → same 422. The notice also calls a private message "a post". Contract was kept to five types on purpose (`AppealRequest`), so the contract and the notice disagree.
Should: either do not make the notice appealable and word it as a message, or accept `DM_MESSAGE` in appeals (service, DTO, contract).

**M2. A priced DM shows in the buyer's token history and the CSV export as "Text answer".** `api/src/units/units.service.ts:357-366` (title chosen only from `POST_VOICE`/`TEXT_FIX`/`EDIT_TEXT`, else "Text answer"); builder put DM spends under `SPEND_POST` (`units.ledger.ts:434`).
Run (H1): after one 150-char DM and one voice DM at prices 5 and 78 tokens, `GET /wallet/history` showed `["SPEND_POST","Text answer",-78000]` and `["SPEND_POST","Text answer",-5000]`; the CSV export says "Text answer" for both. A customer reading a money record sees the wrong label. Only matters once a price above 0 is set (default 0 writes no ledger row).
Should: title "Direct message" / "Voice message" for `DM_TEXT`/`DM_VOICE`.

**M3. Moderator reads of a reported DM are not logged.** `moderation.service.ts:440` (`get`) writes no audit row. Run (MOD1): `auditRowsOnRead: 0` after a moderator opened two reported DMs (one voice, with transcript and a play link). Same as the other item types on origin/main, but a DM is private to two people, so the gap matters more here.
What a moderator can read (run): only the reported message, plus its transcript and a play link for voice; none of the other messages of the conversation (checked by text: earlier and later messages absent). Roles: MODERATOR and ADMIN `200`; EDITOR, ordinary member, the reporter, guest `403/401`. A removal sets the message to `REMOVED`: both people then see `status: REMOVED`, `body: null`, "Message removed"; the voice clip stops playing for the recipient (404) but still plays for the sender (200).
Should: an audit row for opening a DM item (or say plainly that reads are not logged).

### LOW

**L1. Rolling back and then rolling forward again fails.** `migration.sql:5,8,18,19` use `ADD VALUE` without `IF NOT EXISTS`; `rollback.down.sql` keeps the enum values. Run: after a clean rollback I deleted the `_prisma_migrations` row and ran `migrate deploy`: `ERROR: enum label "DM" already exists`. A rollback then a redeploy of the same migration needs a manual fix. Use `ADD VALUE IF NOT EXISTS`.

**L2. Builder's claim "sends share the post rate bucket" is false.** Run (R1): 20 DMs then 2 more → 2×`429 RATE_LIMITED`; then an answer to a question → `201`, with `RateLimit-Remaining: 19`. And 20 answers then a DM → `201`. Reason (read): `@UseGuards(RateLimitGuard)` makes one guard instance per module, so the "post" counter in `DmModule` is a separate in-memory map from the talk module's. The result is better than the claim (no cross-blocking, so no defect), but the DM has its own 20 per 10 minutes, per process, reset on every restart. The builder report and any doc should say so.

**L3. A legacy extra-voice token on a DM clip is only held, not used up.** Run (M3): a clip made with purpose `DM` and an available token; the DM was sent and charged 78 tokens to the wallet; token stayed `RESERVED` (never consumed, never released) until the stale sweep (`units.tokens.ts:23`, `voice.token_reserve_expiry_minutes`) frees it. Nothing is lost, the token is locked for that window. Should: refuse `extraVoiceTokenId` when `purpose` is `DM`, or release it on send.

**L4. `GET /dm/with/{userId}` returns the profile card (handle, display name, state) of anyone who blocked the caller** (200 with `acceptsMessages:false`). Handle is public elsewhere, so low. `dm.service.ts:543-572`.

**L5. A DM costs a `Charge` row even at price 0.** Run (M0): text + voice with prices 0: `ledgerTxns 0`, wallet row unchanged (balance 0, no change), `freePostsRemaining` still 10; but two `Charge` rows (`DM_TEXT`, `DM_VOICE`, cost 0) and two usage counters exist. No money moves, but it is a row per message; and it means rollback of the migration always refuses once any DM exists (it would anyway).

**L6. Messages to a deleted person stay as plaintext.** Run (D1): recipient account purged; the sender's messages to them stay `PUBLISHED` with body; rows the deleted person sent become `DELETED_BY_AUTHOR`, body `NULL`, clips `REMOVED`. The other person sees the tombstone name `deleted-xxxxxxxxxxxx`, `deleted:true`, no place. Reasonable (they are the other person's words) but should be written in the privacy text.

## Answers to the numbered questions

1. **Third person / guest.** Run (P1): another person's conversation id on messages, read, mute, unmute → `404 NOT_FOUND`, no text in the body; report of someone else's message → `404`; a random or non-uuid id → `404`; list returns only their own; `with/{A}`/`with/{B}` from a third person → `conversationId: null`; guest (no token, or `X-Guest-Id`) on every route → `401`. There is no route that takes a conversation id for sending: send takes `toUserId`, so a third person cannot send "into" it. Ids are uuid v7 (time-ordered, 74 random bits); every route checks membership, so guessing gives nothing. Read: the only recipient of a report is the person sent to (`engagement.service.ts`), the sender gets 404 on their own message.
2. **Voice clip.** Run (P2): before sending only the owner plays it; after sending sender and recipient get `200` on `/voice-clips/{id}/play`, a third person and a guest get `404` on both play and metadata. The play link is a signed, expiring link (an `expiresAt` about 15 minutes ahead in the fake store; the real store is read only: `store.signedGet`). Transcript: only in the recipient's and sender's message view and in the moderator detail (run: not visible to a third person via `/voice-clips/{id}`). Read: no search, feed, share, weekly, export or ads query joins a DM clip's transcript (every transcript query is joined to answers/replies/proposals or to the owner's own ad clip). The sender cannot delete a clip in a message (`409`). Voice DMs are transcribed by the same worker as every other clip, so the recording goes to the transcription provider: not proved against the real provider (not called); it belongs in the privacy text.
3. **Anonymous posts.** Run (P3): an anonymous answer's detail and the question's answer list contain neither the author's id nor handle. The DM routes need a user id to act (`with/{id}`, `toUserId`), and there is no route that turns an answer id into a user id. Not proved for every feed, share and profile route (read only: `author: a.anonymous ? null`).
4. **Moderation.** See M3 above: only the reported message; MODERATOR and ADMIN; read not logged; removal effect as stated; no mail (the builder skipped it) but an in-app notice (see M1).
5. **Blocks and states.** Table (run B1): ok 201; blocked either way `403 blocked`; messages off `403 dm_closed`; receiver suspended/banned/deletion pending `403 recipient_unavailable`; receiver deleted or unknown `404`; sender deletion pending `403 FORBIDDEN "Finish setting up your profile first."`; sender banned/suspended `403 ACCOUNT_SUSPENDED`; sender deleted (token still valid) `403 FORBIDDEN`. After a block both people's inbox lists are empty, unread excludes it, `with/` says `acceptsMessages:false`, `conversationId:null`. With "messages off" set after a first message, sending again is `403 dm_closed` and the receiver can still read the old conversation (`200`). See H1 for the distinguishability.
6. **Account deletion.** See L6 and D1. Messages sent become tombstones, clips `REMOVED` (files removed by the existing media housekeeping, not run here), mutes deleted, ledger/charge rows stay. Data export leaves DMs out; people may expect their own messages in a data request, so yes, the privacy text needs a line (a person's DMs are not in the export; deleted accounts' messages to others stay; voice messages are transcribed).
7. **Logs.** Run (L1 log capture, stdout+stderr over: text send, voice send with transcript, a 422, a list, a store failure): the only line was the `AllExceptionsFilter` error with the exception text; no body, transcript, email or phone appeared. Not a proof about the production log shipper.
